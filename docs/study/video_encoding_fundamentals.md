# 비디오 인코딩 기초: CRF, 야간 용량 폭증, LeRobot 비교

**날짜:** 2026-04-17

이 문서는 비디오 인코딩 도메인에 익숙하지 않은 개발자를 위해, 본 프로젝트의 녹화 파이프라인에서 핵심이 되는 개념들을 설명한다. 특히 **야간 용량 폭증 문제**의 근본 원인과 해결책, 그리고 **LeRobot ML 학습용 데이터셋**과의 품질 설정 차이를 다룬다.

## 1. CRF (Constant Rate Factor) 란?

### 한 줄 요약

CRF는 "일정한 **화질**을 유지하면서 bitrate는 자유롭게 변동시키는" 인코딩 모드이다.

### 동작 원리

```
┌──────────────────────────────────────────────────────────┐
│                    CRF 인코딩 모드                         │
│                                                          │
│  입력 프레임 ──► 인코더가 장면 복잡도를 분석                   │
│                     │                                    │
│        ┌────────────┴────────────┐                       │
│        ▼                        ▼                       │
│   단순한 장면                복잡한 장면                    │
│   (흰 벽, 정적)             (나뭇잎, 빠른 움직임)           │
│        │                        │                       │
│   적은 bits 할당             많은 bits 할당                │
│   (bitrate ↓)               (bitrate ↑)                 │
│        │                        │                       │
│        └────────────┬───────────┘                       │
│                     ▼                                    │
│            화질은 동일하게 유지됨                            │
│            (CRF 값이 정의하는 품질 수준)                     │
└──────────────────────────────────────────────────────────┘
```

### CRF 스케일: 0 ~ 51

libx264의 CRF 범위:

| CRF | 의미 | 용도 |
|-----|------|------|
| 0 | 무손실 (lossless). 모든 픽셀 원본 유지 | 영상 제작/아카이빙 (용량 거대) |
| 18~22 | 고품질. 원본과 구분 어려움 | Netflix (18~20), 소비자 미디어 |
| **23** | **ffmpeg 기본값**. 범용 고품질 | 일반 웹 영상 |
| 28~30 | 운영/감시용. 확인 목적에 충분 | 로봇 녹화 운영, ML 학습 데이터 |
| 35~51 | 눈에 띄는 화질 저하 | 거의 사용 안 함 |

**핵심 규칙: CRF가 6 증가할 때마다 bitrate(파일 크기)가 대략 절반으로 줄어든다.**

```
CRF 23 ──(+5)──► CRF 28: bitrate 약 1/3
CRF 23 ──(+7)──► CRF 30: bitrate 약 1/4~1/5
```

## 2. CRF vs CBR vs VBR — 세 가지 인코딩 모드 비교

| 모드 | 무엇이 고정? | 무엇이 변동? | 비유 |
|------|------------|------------|------|
| **CRF** (Constant Rate Factor) | 화질 | bitrate | "품질 맞춤 양복" — 비용(bits)은 재료에 따라 달라지지만 결과물 품질은 항상 동일 |
| **CBR** (Constant Bit Rate) | bitrate | 화질 | "정액 요금제" — 매초 같은 bits를 쓰므로 어려운 장면에서 화질이 떨어짐 |
| **VBR** (Variable Bit Rate) | 평균 bitrate | 순간 bitrate | "예산 내 변동" — 어려운 장면에 bits를 몰아주되 전체 평균은 유지 |

**CRF가 생성하는 결과물은 VBR이다.** CRF는 "화질 고정 → bitrate가 자유변동"이므로, 출력 파일의 bitrate 그래프는 장면 복잡도에 따라 크게 요동친다.

```
bitrate
  ↑
  │    ╱╲         장면 전환/복잡          ╱╲
  │   ╱  ╲        ↓                    ╱  ╲
  │  ╱    ╲      ╱╲╱╲                 ╱    ╲
  │ ╱      ╲    ╱    ╲               ╱      ╲
  │╱        ╲──╱      ╲─────────────╱        ╲──
  │          정적 장면      정적 장면           정적
  └─────────────────────────────────────────────► 시간

  CRF 모드: 화질은 일정, bitrate는 장면에 따라 자유 변동
```

## 3. 야간 카메라 노이즈와 용량 폭증

이것이 본 프로젝트에서 가장 중요한 운영 이슈이다.

### 3.1 왜 어두우면 노이즈가 생기는가?

카메라 센서는 빛(광자)을 전기 신호로 변환한다. 밝을 때는 신호가 강해서 노이즈가 묻힌다.

```
┌─ 밝은 환경 ─────────────────────────────────────┐
│                                                 │
│  광자 많음 → 신호 강함 → 노이즈 비율 낮음 (SNR 높음) │
│                                                 │
│  신호: ████████████████████                       │
│  노이즈:  ░░                                     │
│  결과: 깨끗한 이미지                                │
└─────────────────────────────────────────────────┘

┌─ 어두운 환경 ────────────────────────────────────┐
│                                                 │
│  광자 적음 → 신호 약함 → 카메라가 gain(ISO) 증폭    │
│  → 신호와 함께 노이즈도 증폭됨 (SNR 낮음)           │
│                                                 │
│  신호:   ███                                     │
│  노이즈: ░░░░░░░░░░░░░░░░░                       │
│  결과: 지글지글한 grain 노이즈가 매 프레임 랜덤 발생  │
└─────────────────────────────────────────────────┘
```

**비유:** 조용한 방에서 소곤소곤 말하면 명확하게 들린다 (높은 SNR). 하지만 공사장에서 같은 크기로 말하면 소음에 묻힌다 (낮은 SNR). 카메라의 "볼륨 올리기" (gain 증폭) = 마이크 감도를 최대로 올리는 것. 목소리도 커지지만 소음도 같이 커진다.

### 3.2 왜 노이즈가 인코더를 망가뜨리는가?

H.264 인코딩의 핵심은 **프레임 간 예측 (inter-frame prediction)** 이다:

```
┌─ 정상 동작 (밝은 환경) ─────────────────────────────┐
│                                                    │
│  프레임 N:   [벽, 테이블, 의자]                       │
│  프레임 N+1: [벽, 테이블, 의자]  ← 거의 동일!          │
│                                                    │
│  인코더: "N+1은 N과 같다" → 차이(잔차)만 저장           │
│  잔차: 거의 0 → 매우 적은 bits 소모                    │
│                                                    │
│  결과: bitrate 50~400 kbps (매우 작음)               │
└────────────────────────────────────────────────────┘

┌─ 문제 상황 (어두운 환경) ──────────────────────────────┐
│                                                     │
│  프레임 N:   [벽 + 랜덤 노이즈 패턴 A]                 │
│  프레임 N+1: [벽 + 랜덤 노이즈 패턴 B]  ← 완전히 다름!  │
│                                                     │
│  인코더: "N+1은 N과 다르다" → 큰 잔차를 저장해야 함      │
│  잔차: 노이즈 차이 = 모든 픽셀이 변경 → 엄청난 bits 소모  │
│                                                     │
│  결과: bitrate 1~20 Mbps (폭증!)                     │
└─────────────────────────────────────────────────────┘
```

**핵심 원인: 랜덤 노이즈는 프레임마다 완전히 다른 패턴을 만든다.** 장면 자체는 정적(벽, 빈 방)이지만, 노이즈가 매 프레임 랜덤으로 바뀌므로 인코더 입장에서는 "모든 픽셀이 매 프레임 변하는 극도로 복잡한 영상"으로 인식한다.

### 3.3 시간 복잡도(Temporal Complexity) vs 공간 복잡도(Spatial Complexity)

인코더가 보는 "복잡도"에는 두 종류가 있다:

| 복잡도 유형 | 의미 | 노이즈의 영향 |
|-----------|------|-------------|
| **공간 복잡도** (Spatial) | 한 프레임 안에서 디테일이 얼마나 많은가 (텍스처, 엣지) | 노이즈가 고주파 디테일을 추가 → I-프레임 크기 증가 |
| **시간 복잡도** (Temporal) | 연속 프레임 간 차이가 얼마나 큰가 (움직임, 변화) | **이것이 치명적.** 노이즈가 인공적으로 최대 시간 복잡도를 생성 |

**비유:**
- 공간 복잡도 = 한 장의 사진이 얼마나 복잡한가 (풍경 vs 흰 벽)
- 시간 복잡도 = 동영상에서 프레임 간 변화가 얼마나 큰가 (정지 화면 vs 액션 영화)

노이즈는 정적인 장면을 "매 프레임 모든 픽셀이 바뀌는 영상"으로 만든다 → **인위적으로 시간 복잡도를 최대화**.

### 3.4 실측 데이터 (본 프로젝트, 640x480@30fps, CRF 23)

MGOTEST 24시간 녹화에서 관측된 실제 편차:

| 시간대 | Bitrate | 1시간 크기 | 원인 |
|--------|---------|-----------|------|
| 저녁 (조명 안정) | ~50 kbps | ~22 MB | 정적 장면, 압축 효율 최고 |
| 자정~새벽 (저조도) | ~1 Mbps | ~420 MB | 센서 noise grain → inter-frame 예측 실패 |
| 일출 (조명 전환) | ~1.35 Mbps | ~580 MB | noise + 급변 조명 |
| 오전 (밝음) | ~55 kbps | ~24 MB | 다시 압축 효율 회복 |

**야간 bitrate는 주간 대비 최대 27배.** 하루 24시간 중 야간(약 10시간)이 전체 저장 용량의 대부분을 차지한다.

## 4. 해결책: `--maxrate` + `--bufsize`

### 4.1 CRF만 높이면 안 되는 이유

CRF 28로 올리면 bitrate가 약 1/3로 줄지만, 야간 노이즈의 근본적인 "시간 복잡도 폭증"은 여전하다:

```
CRF 23 야간: ~1,000 kbps   →   CRF 28 야간: ~400 kbps (여전히 주간의 6~7배)
CRF 23 주간:    ~50 kbps   →   CRF 28 주간:  ~20 kbps
```

CRF를 올리면 전체적으로 줄어들지만, 야간/주간 **편차 비율**은 크게 변하지 않는다.

### 4.2 `-maxrate`와 `-bufsize`가 하는 일

`-maxrate`는 **bitrate 상한선(ceiling)**이다. 인코더가 아무리 bits를 쓰고 싶어도 이 한도를 넘지 못한다.

```
┌─ CRF 28만 사용 ──────────────────────────────────┐
│                                                  │
│  bitrate                                         │
│   ↑    ╱╲                                        │
│   │   ╱  ╲      ← 야간 스파이크 (제한 없음)        │
│   │  ╱    ╲                                      │
│   │ ╱      ╲                                     │
│   │╱        ╲────────╱╲──                         │
│   └───────────────────────────► 시간              │
└──────────────────────────────────────────────────┘

┌─ CRF 28 + maxrate 2M 사용 ───────────────────────┐
│                                                  │
│  bitrate                                         │
│   ↑ ─ ─ ─ ─ ─ ─ ─ ─ 2M ceiling ─ ─ ─ ─ ─ ─ ─  │
│   │   ╱─────╲   ← 스파이크가 2M에서 잘림!          │
│   │  ╱       ╲                                   │
│   │ ╱         ╲                                  │
│   │╱           ╲─────╱╲──                        │
│   └───────────────────────────► 시간              │
└──────────────────────────────────────────────────┘
```

`-bufsize`는 인코더가 bitrate 상한을 얼마나 **엄격하게** 지킬지를 결정한다:

| bufsize 비율 | 의미 | 용도 |
|-------------|------|------|
| `bufsize = 1× maxrate` | 매 1초 단위로 maxrate 준수 (엄격) | 라이브 스트리밍 |
| `bufsize = 2× maxrate` | 2초 단위로 평균 maxrate 준수 (표준) | **파일 녹화 (권장)** |
| `bufsize = 4× maxrate` | 4초 단위 (느슨) | 장기 평균만 중요할 때 |

**비유:** 월 식비 예산이 50만원 (`maxrate`)이라면:
- `bufsize = 1×`: 매주 정확히 12.5만원 이내로 써야 함 (엄격)
- `bufsize = 2×`: 이번 주 15만원 쓰면 다음 주 10만원으로 보전 가능 (유연)
- `bufsize = 4×`: 이번 달 초에 몰아쓰고 나중에 아끼면 됨 (느슨)

### 4.3 CRF + maxrate 조합 시 동작

maxrate가 설정되면 **CRF는 "목표"가 되고 "보장"이 아니게 된다:**

- 쉬운 장면: CRF 품질을 달성하고도 maxrate 이내 → CRF 품질 그대로 유지
- 어려운 장면: CRF 품질을 달성하려면 maxrate를 초과해야 함 → **화질을 낮춰서** maxrate 이내로 유지

즉, 야간 노이즈 장면에서는 의도적으로 화질이 떨어지지만, 어차피 **어두운 장면의 노이즈는 의미 없는 정보**이므로 운영상 문제없다.

### 4.4 본 프로젝트 권장 설정

```bash
# 운영 녹화 (24시간 상시 녹화, 파일 크기 제어 중요)
python3.10 camera_recorder.py --branch-id BB003 --ffmpeg --crf 28 --maxrate 2M

# 개발/테스트 (품질 우선)
python3.10 camera_recorder.py --branch-id TEST --ffmpeg
# → 기본값 CRF 23, maxrate 없음
```

### 4.5 설정별 예상 야간 1시간 세그먼트 크기

640x480@30fps 기준, 야간 저조도 (최악 시나리오):

| 설정 | 야간 bitrate | 1시간 크기 | 기본 대비 |
|------|-------------|-----------|----------|
| CRF 23 (기본) | ~1 Mbps | ~420 MB | 기준 |
| CRF 28 | ~400 kbps | ~170 MB | 60% 감소 |
| CRF 28 + maxrate 2M | **≤2 Mbps (cap)** | **≤100 MB** | **75%+ 감소** |
| CRF 30 + maxrate 1.5M | ≤1.5 Mbps | ≤70 MB | 83% 감소 |

> **참고:** 실제 야간 bitrate가 maxrate 미만이면 cap이 작동하지 않으므로, CRF 28 + maxrate 2M은 대부분의 야간 장면에서 CRF 28 단독과 비슷하다. maxrate는 **극단적 스파이크를 방지하는 안전장치**이다.

## 5. CRF 기본값이 23인 이유, 그리고 왜 28~30으로 가는가

### 5.1 ffmpeg이 23을 기본값으로 선택한 이유

ffmpeg의 CRF 23은 **"범용 시청용 영상"** 을 타겟으로 설계되었다:

- 일반 디스플레이에서 원본과 구분하기 어려운 품질
- 영화, 유튜브 업로드, 홈비디오 등 **사람이 주의 깊게 보는 콘텐츠** 기준
- "시각적으로 투명(visually transparent)" 수준

### 5.2 운영 녹화에서 28을 권장하는 이유

로봇 녹화는 소비자 영상과 근본적으로 다른 사용 패턴:

| 관점 | 소비자 영상 (CRF 23) | 로봇 운영 녹화 (CRF 28) |
|------|--------------------|-----------------------|
| 시청 빈도 | 대부분 시청됨 | 대부분 시청 안 됨 (사고 시에만 확인) |
| 시청 목적 | 감상, 평가 | "X가 Y 시각에 일어났나?" 확인 |
| 화질 민감도 | 높음 (배경 선명도도 중요) | 낮음 (물체/사람 식별이면 충분) |
| 저장 비용 | 1회성 (편집 후 삭제) | 누적 (24h × 365일 × N대 로봇) |

**CRF 23 → 28 변경 시 화질 차이:** 전문가가 두 영상을 나란히 놓고 비교해야 겨우 차이를 인식하는 수준. 운영 목적의 "이 시각에 무슨 일이 있었나?" 확인에는 전혀 지장 없음.

### 5.3 그럼 왜 28이 기본값이 아닌가?

본 프로젝트 코드의 `--crf` 기본값은 23 (ffmpeg 원래 기본값 유지):

- **기존 녹화 데이터와의 일관성** — 기존 CRF 23으로 녹화된 데이터와 섞어도 품질이 갑자기 바뀌지 않음
- **안전한 기본값** — 새 사용자가 설정 없이 실행해도 품질 불만 없음
- **의도적 선택을 유도** — `--crf 28`을 명시적으로 설정 = 운영자가 트레이드오프를 인지하고 결정

## 6. LeRobot 데이터셋과의 비교: 왜 CRF 30인가?

### 6.1 LeRobot이 CRF 30을 쓰는 이유

LeRobot (Hugging Face의 로봇 학습 프레임워크)은 ML 학습용 비디오 데이터셋에 CRF 30을 표준으로 사용한다:

**ML 모델은 사람과 다르게 영상을 "본다":**

```
┌─ 사람의 시각 ─────────────────────────────────┐
│                                              │
│  "이 장면이 선명한가? 자연스러운가?"              │
│  → 높은 CRF = 블록 아티팩트 감지 → 불쾌         │
│  → CRF 23 이하를 선호                          │
└──────────────────────────────────────────────┘

┌─ ML 모델의 "시각" ────────────────────────────┐
│                                              │
│  "그리퍼가 열렸나? 물체가 어디 있나?"             │
│  → 통계적 특징(feature) 추출                    │
│  → CRF 30의 아티팩트는 task-relevant 특징과      │
│    상관없음 → 학습 성능에 영향 거의 없음           │
└──────────────────────────────────────────────┘
```

**추가 이유:**
- **데이터셋 규모:** 수천 시간의 시연 데이터를 저장. CRF 23 대비 4~5배 작은 용량 = 저장비 + I/O 대역폭 절감
- **Data augmentation과의 관계:** 학습 파이프라인이 이미 random crop, color jitter, brightness 변형을 적용. 이 변형이 CRF 30 아티팩트보다 훨씬 큼. 모델이 augmentation에 강건하면 CRF 30에도 강건함

### 6.2 CRF 비교 표: 23 vs 28 vs 30

640x480@30fps, `-preset medium` 기준:

| | CRF 23 | CRF 28 | CRF 30 |
|---|--------|--------|--------|
| **주 용도** | ffmpeg 기본, 범용 | 운영 녹화 권장 | ML 학습 데이터 |
| **밝은 정적 장면** | ~200 kbps | ~70 kbps | ~50 kbps |
| **밝은 동적 장면** | ~1,500 kbps | ~500 kbps | ~350 kbps |
| **야간 노이즈 (정적)** | ~4,000 kbps | ~1,500 kbps | ~1,000 kbps |
| **야간 노이즈 (동적)** | ~10,000+ kbps | ~4,000 kbps | ~2,500 kbps |
| **1시간 주간 평균** | ~50 MB | ~18 MB | ~12 MB |
| **1시간 야간 평균** | ~420 MB | ~170 MB | ~110 MB |
| **화질 (주관적)** | 원본과 거의 동일 | 확대해야 차이 보임 | 세밀 텍스처 손실 |

### 6.3 녹화 시점 CRF vs 배포 시점 CRF

중요한 설계 원칙:

```
녹화 (camera_recorder.py)        배포 (미래 LeRobot 변환)
┌────────────────────┐          ┌────────────────────┐
│ CRF 28 + maxrate   │ ──저장──► │ 필요 시 CRF 30으로   │
│ (운영 품질 보존)     │          │ 재인코딩 가능         │
└────────────────────┘          └────────────────────┘

  CRF 28로 녹화 → CRF 30으로 재인코딩 ✅ (정보는 줄지만 가능)
  CRF 30으로 녹화 → CRF 28로 복원     ❌ (손실된 정보는 복구 불가)
```

따라서 **녹화 시점에는 CRF 28 (약간 높은 품질) 로 보존**하고, ML 학습용 데이터셋 변환 시 CRF 30으로 재인코딩하는 것이 합리적이다.

## 7. 추가 최적화 후보 (리서치 단계)

현재 CRF + maxrate로 야간 문제의 75%+ 절감이 가능하지만, 추가 최적화 방안도 있다:

### 7.1 사전 디노이즈 필터 (`-vf hqdn3d`)

```bash
ffmpeg ... -vf hqdn3d=4:3:6:4 -c:v libx264 -crf 28 ...
```

노이즈를 인코딩 전에 제거 → 인코더가 보는 시간 복잡도 자체가 감소 → bitrate 50~80% 추가 절감 가능. 단, **CPU 부하 증가**하므로 로봇 하드웨어에서 실시간 처리 가능한지 벤치마크 필요.

### 7.2 야간 FPS 감소

어두운 환경에서 프레임 수를 30fps → 15fps로 줄이면 bitrate가 약 절반. 야간 영상의 정보 가치가 낮으므로 FPS 감소의 실질적 손실이 적음. 단, 구현 복잡도 증가 (시간대 감지, 동적 fps 전환).

### 7.3 센서 gain 상한 설정

RealSense 카메라의 auto gain을 제한하면 근본적으로 노이즈 발생을 억제. 가장 효과적이지만 카메라 하드웨어/드라이버 수준의 설정이 필요.
